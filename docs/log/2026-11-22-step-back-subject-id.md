# 回头看：人物编号“不改、不复用”两次没有完全守住

同一个问题改了两次还没解决时写这份记录。写完交给创始人，确认之后再动代码。

- 日期：2026-11-22
- 谁写的：总协调

## 1. 问题是什么，已经试过什么

决策 0007 说人物编号是网址的一部分，只增不改、不复用。

- **第一次（格式 5 初版）：** 只在注释和决策里写了这句话，数据库没有强制。
  Fable 5.2 审查发现：删掉一个人后，编号会自动分给下一个新人物，网址会串到另一个人身上。
- **第二次（修复）：** 编号改成只增不复用（`AUTOINCREMENT`），加了一个触发器 `subjects_id_fixed`，禁止修改编号。
  复查发现：这个触发器只在语句里写 `id` 时才会被触发。SQLite 允许用 `rowid`、`oid`、`_rowid_`
  三个别名指同一列，写别名就绕过去了，仍然能改编号，进而让旧编号指向新的人。

账本本身没有受影响，其余所有发布规则都守住了。被绕过的只是“编号不变”这一个承诺。
要触发它，代码必须故意写 `rowid`、`oid` 或 `_rowid_`，正常代码不会这样写。

## 2. 当初的技术路线和假设

假设“禁止改 `id` 这一列”就等于“编号不能改”。不成立：在 SQLite 里同一列有四个名字，
只挡住一个名字不够。这不是路线错误，是一个触发器条件写窄了。

## 3. 三条路

- **换实现方式：** 把触发器的条件从“改了 `id` 这一列时”放宽为“对人物表的任何修改，只要编号变了就拒绝”。
  审查方已在临时副本上试过：四种写法全部被拒绝，改名字仍然可以。改动是一行，再补一项测试。
  代价几乎为零。
- **改路线：** 不在数据库里防，把“写 `rowid`、`oid`、`_rowid_`”加进代码审查的退回清单，和“插入人物时指定编号”同样处理。
  代价是这一条又多靠一份人工规则。
- **这件事本身不该做：** 放弃“编号永不改变”，网址改用名字。会重新遇到同名和改名的问题，
  正是你在决策 0007 里否决的。

## 4. 建议

选第一条：一行改动，堵住的是正常写法之外的唯一一条路，不增加触发器的数量，也不增加人工规则。
同时把复查顺带指出的四个常见隐形字符（U+2060、U+200C、U+200D、U+00AD）加进“空白”清单。
改完后只请一次 Opus 5.5 的日常审查确认这一行，不再动用 Fable 5.2。
